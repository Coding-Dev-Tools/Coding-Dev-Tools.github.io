Gate your deploys on config drift — fail the build before prod finds out

Staging and production configs drift quietly: one incident fix touches prod only, three weeks later a routine deploy behaves differently per environment. A one-line CI step makes that a build failure instead of a 2 a.m. page.

The gate: --output silent

ConfigDrift is an MIT-licensed Python 3.10+ CLI that compares config files or whole environment directories and classifies drift by severity. For CI, use silent output: the command exits 0 when there is no breaking drift and 1 when breaking drift is found.

pip install git+https://github.com/Coding-Dev-Tools/configdrift.git

configdrift check ./config/staging/app.yaml ./config/prod/app.yaml --output silent
# exit 0 = no breaking drift · exit 1 = breaking drift → CI fails

By default only breaking drift fails the gate. Keys like database*, auth*, api_key*, secret*, password*, token*, and endpoint* are classified breaking out of the box. Add --strict if you want any drift — not just breaking changes — to fail the build.

GitHub Actions example

- name: Detect config drift
  run: |
    pip install git+https://github.com/Coding-Dev-Tools/configdrift.git
    configdrift check ./config/staging/app.yaml ./config/prod/app.yaml --output silent

For monorepos with several services, compare whole directories at once:

configdrift scan ./config/staging ./config/prod --baseline staging --output silent

Tuning the gate

  • Severity rules: review which keys count as breaking in your project settings; the defaults match where most teams get paged.
  • Baselines: pass --baseline/--target to make direction explicit when comparing environments.
  • Noise control: large scans are slower — narrow the scan to changed files or a single directory.
